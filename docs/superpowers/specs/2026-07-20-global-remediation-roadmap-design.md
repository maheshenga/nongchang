# 全局架构与功能闭环修复设计

## 背景与目标

当前系统已经具备真实的多租户、地块、批次、农事、溯源、防伪、农资、计费、AI、上传和第三方集成链路，但全量审查仍发现账号开通、发布制品、多端入口、路由、接口契约和运维控制之间存在断点。

本轮按 P0 -> P1 -> P2 顺序完成所有已确认问题，目标是：

1. 新建商户首次登录即可使用其被授权的核心业务功能。
2. 发布产物能够在全新宝塔发布目录独立安装、迁移、启动和回滚。
3. Web、小程序和后台配置不再展示虚假、重复或不可达功能。
4. 后台页面具备可刷新、可回退、可收藏的稳定路由。
5. 菜单、角色、能力和接口响应具备可持续验证的统一契约。
6. 看板、防伪、审计和后台任务反映真实生产状态。
7. 完成热点拆分、分页搜索和不可达代码清理，降低后续扩展成本。

## 方案比较

### 方案 A：一次性重写后台壳、权限和发布系统

优点是最终结构统一；缺点是同时改变认证、路由、菜单、部署和多端协议，回归面过大，也无法为每个业务断点提供独立通过证据。本轮不采用。

### 方案 B：按纵向业务闭环分阶段修复（采用）

每个阶段覆盖 Shared 契约、Backend、Web/Miniapp、迁移和测试中的必要部分。旧接口和旧二维码地址在兼容期继续可用，每阶段都能独立回滚应用代码。该方案最符合当前模块化单体和单服务器宝塔部署现实。

### 方案 C：只修界面和部署脚本，不调整公共契约

短期改动最小，但会保留菜单/权限漂移、类型强转和旧小程序兼容风险，问题会在下一轮扩展中重新出现。本轮不采用。

## 全局约束

- 不使用 `using-superpowers`。
- 不削弱 `JwtAuthGuard`、`RolesGuard`、`PermissionsGuard`、`ScopeService` 或数据库租户约束。
- 不改变冻结码、额度预约、AI 模糊结果隔离和支付验签语义。
- 不把演示看板中的模拟数据包装为生产数据。
- 旧 `/api` 和既有 `#/trace/:code` 在 API 版本迁移期间保持兼容。
- 所有生产代码改动先有能证明旧行为失败的回归测试。
- 敏感配置只通过环境变量、GitHub Environment 或宝塔受限配置提供，不进入仓库和聊天记录。
- 每个阶段通过定向测试；最终通过完整生产、浏览器、可访问性、查询计划和发布制品门禁。

## 阶段 1：商户开通与用户组权限闭环（P0）

### 问题

后台创建商户时未写入 `groupId`。商户不在权限旁路角色中，因此首次登录后会被权限守卫拒绝地块、批次、农事和溯源读取。虽然存在用户组分配接口，但 Web 没有消费它；代理管理员还会看到只有系统管理员才能执行的新建、编辑和删除按钮。

### 设计

- `CreateUserDto` 增加可选 `groupId`，仅允许当前租户内的组。
- 创建 `merchant` 或 `member` 时，未指定组则解析当前租户默认组并写入；没有默认组时沿用现有并发安全的 `ensureDefault()`。
- 商户列表返回 `groupId` 和 `groupName`，不返回权限内部存储细节。
- 商户管理页支持创建时选择组、编辑时重新分组。
- 系统管理员可维护组；代理管理员只读组定义，但可给自己辖区内商户分组。
- 菜单与按钮根据真实能力隐藏，不依赖提交后等待 403 来表达权限。

### 验收

- 新建商户首次登录可读取地块、批次、农事和溯源。
- 指定组、默认组和跨租户非法组均有测试。
- 代理管理员页面不存在其无法执行的用户组 CRUD 控件。
- 分组后权限立即生效，现有 session validation cache 被失效。

## 阶段 2：可独立部署的宝塔发布制品（P0）

### 问题

当前制品只有编译目录、迁移目录、根清单和锁文件，缺少可解析的后端运行包、Prisma schema 和生产依赖；宝塔源码构建文档与不可变制品手册也互相冲突。

### 设计

- CI 在 Linux 上构建一个可移植 `server/` 目录，包含后端编译产物、Prisma schema/migrations、包清单和锁定的生产依赖。
- `web/` 保持纯静态构建产物；`shared` 作为后端部署包依赖注入，不再要求服务器存在仓库工作区。
- 制品清单记录目标平台、Node/pnpm 版本、Git SHA、文件哈希和制品类型。
- 新增制品验证器：在临时空目录解包，验证 Node 可解析所有运行依赖、Prisma schema 可加载、后端入口存在。
- 宝塔部署只解包已验证制品到版本目录，不在生产机重新编译。
- 迁移预检、前向迁移、待命端口启动、readiness、SHA smoke、切流和应用回滚形成一个脚本化流程。
- GitHub workflow 只引用 Environment secrets；默认构建并上传，真实服务器切换仍由显式手动批准触发。
- 小程序建立独立构建制品和微信上传手册，不混入 Web/API 服务器包。

### 验收

- 在没有源码和旧 `node_modules` 的临时目录能够启动到环境校验边界。
- 制品可以运行 `prisma migrate status/deploy` 所需文件。
- 发布文档只有一条权威流程，旧源码构建说明明确标记为开发部署。
- workflow 不包含主机密码、私钥、数据库密码或应用密钥。

## 阶段 3：客服配置与小程序流程真实性（P0/P1）

### 设计

- `TenantSettings` 增加可空 `supportContact`，系统管理员在后台配置；小程序读取失败或未配置时只提示联系平台管理员。
- 删除硬编码 `400-000-0000`。
- “我的 -> 溯源记录”直接切换到现有溯源 Tab。
- 批次详情“记一笔”通过短生命周期本地导航意图把 `batchId` 带到工作台，工作台选中批次并定位记录表单；消费后立即清除意图。
- 溯源海报只有在批次存在真实溯源码时才称为“溯源海报”，并包含可扫描的公开 URL 二维码；无可用码时提示先到批次管理生成，不伪造码。
- 蓝牙设备等未实现入口继续明确标记为未开放，不创建空白页面。

### 验收

- 任意生产代码中不再出现占位客服电话。
- 从批次详情进入记录页时保持原批次上下文。
- 海报二维码解析后等于现有公开溯源地址。
- 小程序真机清单覆盖扫码、相机、录音、定位、保存相册和微信登录。

## 阶段 4：真实看板与防伪生产入口（P1）

### 设计

- 新增受作用域保护的 `GET /dashboard/summary`，在数据库侧返回在管批次总数、地块总数、农事总数、累计扫码和最近农事记录。
- Shared 定义完整响应 schema，Web 不再通过受上限影响的列表长度计算总数。
- 防伪监控成为独立生产页面和能力项，对系统管理员、代理管理员、商户按现有作用域开放。
- 演示看板仍可引用真实防伪组件，但不再是唯一入口。

### 验收

- 数据超过 100/500 条时看板仍返回准确总数。
- 三类业务角色只能看到自身作用域统计与防伪数据。
- 生产菜单可直接进入防伪页，会员和平台管理员不可见。

## 阶段 5：正式路由与能力注册表（P1）

### 设计

- 使用成熟 React Router 建立 hash 路由，保留 Nginx 静态站点兼容：`#/app/:tab`、`#/trace/:code`、`#/billing/pay-result`。
- 菜单点击、全局菜单搜索、跨页面跳转、刷新和浏览器前进后退都由路由驱动。
- 使用 Shared `Role` 原值，移除 Web 内部 `merchant_admin` 别名。
- 建立不含图标的共享能力 ID/角色策略；Web 只负责能力到标签、图标和组件的映射。
- 对后端控制器角色元数据与前端能力策略增加契约测试，防止菜单可见但接口必然 403。

### 验收

- 刷新具体后台地址保持当前页面。
- 浏览器返回恢复上一页面，未授权路由落到该角色首个安全页。
- 公共二维码旧地址继续工作。

## 阶段 6：接口版本与运行时契约（P1）

### 设计

- 新接口使用 `/api/v1`；旧 `/api` 在兼容期映射到同一处理器。
- Web 和新小程序构建迁移到 v1，已发布旧小程序继续访问旧路径。
- 为代理商、用户、防伪、AI 服务商、租户、凭证等剩余客户端补齐 Shared Zod 响应 schema，移除裸 `request<T>` 信任。
- 生成受版本控制的 API 路由/契约清单，CI 检查重复路由、无 schema 响应和意外删除。
- 记录版本废弃日期和兼容窗口，删除旧路径必须单独批准。

### 验收

- 所有生产 API 客户端对外部响应做运行时解析。
- v1 与旧路径的鉴权、状态码和响应体一致。
- 旧小程序兼容 E2E 与新客户端契约测试同时通过。

## 阶段 7：业务审计与生产运维门禁（P1）

### 设计

- 新增只追加的 `AuditLog`，记录租户、操作者、动作、资源类型/ID、结果、request ID 和安全元数据；不保存密码、token、密钥、支付原文、AI 提示或上传内容。
- 覆盖租户状态、用户状态/审核/分组、额度充值/分配、码冻结/解冻、租户设置和第三方配置修改。
- 提供按租户和角色受限的审计查询页。
- 单服务器生产预检必须证明 Redis、至少一个 Operations Worker、指标保护、备份目标和有效告警 runbook 已配置。
- 用仓库内真实 runbook 替换 `example.invalid`；生产指标端点必须有 Bearer token 或明确的内网拒绝策略。

### 验收

- 高风险操作成功和失败都有审计证据，且跨租户不可读。
- 审计写失败时高风险写操作按明确策略失败关闭。
- 单服务器配置关闭全部 Worker 或暴露无保护 metrics 时发布预检失败。

## 阶段 8：扩展性、搜索和代码热点（P2）

### 设计

- 将 `BillingService` 按账户余额、预约/恢复、套餐、订单结算拆分，外部控制器契约不变。
- 代理商和商户搜索/状态过滤进入后端分页查询；搜索时重置到第一页。
- 全局搜索若仍只支持菜单，文案改为“搜索菜单”；资源搜索另建聚合接口后再启用。
- 删除或移出生产源码中不可达的 `SystemAdmin`、`AgentPlatform` 和旧移动演示实现，保留必要历史说明而不保留第二套可编译业务代码。
- 为新增集成统一 Provider 接口，但不在本轮新增地图、支付或存储供应商。

### 验收

- 搜索能命中任意分页中的数据。
- 计费行为、事务和幂等测试在拆分前后完全一致。
- 生产构建不再包含不可达旧实现。

## 实施与提交策略

每个阶段独立执行 RED -> GREEN -> REFACTOR，并形成一个或多个职责单一的提交。阶段完成后进行：

1. 定向单元测试和类型检查。
2. 代码审查，重点检查租户、角色、秘密、事务和兼容边界。
3. 相关 E2E/浏览器或制品测试。
4. 工作树检查后提交。

最终门禁至少包括：

```powershell
pnpm verify:production
pnpm test:browser
pnpm test:accessibility
pnpm --filter @nongchang/backend db:query-plans
pnpm backup:verify-restore -- --output-dir "$env:TEMP\nongchang-remediation-backup-drill"
node --test scripts/lib/backup-format.test.mjs scripts/release/*.test.mjs
```

小程序另外执行生产构建和真机验收；无法自动证明的微信平台、支付回调、OSS 和服务器切流步骤必须单独列出，不以单元测试替代。

## 完成定义

- 本文所有阶段验收项均有实现与可执行证据。
- P0 问题全部关闭后才允许进行正式生产切换。
- P1/P2 不以“后续优化”保留在生产菜单中；若外部条件阻塞，入口必须真实降级并记录明确阻塞证据。
- 最终代码审查无新的 P0/P1 问题，所有提交已推送到受保护分支并通过 CI。
