# 全量缺陷加固设计

## 目标

按已确认的 P1 → P2 优先级修复本轮审查发现的全部问题，同时保持现有多租户、权限、支付和公开溯源契约的安全边界：

1. 地块创建必须原子化，失败不得留下半成品记录。
2. 公开溯源默认不得泄露精确地块坐标。
3. 小程序快速切换批次时不得展示错配的溯源事件。
4. Web 全局对话框必须正确处理并发请求。
5. 扫码计数、防伪明细和公开响应必须保持一致。
6. 地块创建响应必须反映数据库最终坐标状态。
7. SaaS 品牌、行业和默认作物文案必须由后台数据驱动。

## 非目标

- 不重写现有认证、权限、支付或计费架构。
- 不改变冻结码“暂停公开展示、内部仍可用于授权作业”的现有语义。
- 不把显式标注的演示看板改造成生产功能。
- 不引入新的消息队列、地图供应商或第三方配置中心。
- 不在本轮增加地块多边形、电子围栏或空间邻近查询。

## 总体方案

采用最小增量方式扩展现有 NestJS、Prisma、Shared DTO、React 和 Taro 边界：

- 数据一致性问题优先在数据库事务层解决。
- 公共隐私策略和 SaaS 文案统一落在租户级配置中。
- Web 与小程序通过受保护的当前租户配置接口读取同一份数据。
- 公开溯源只接收已投影、已脱敏的数据，不让前端自行决定隐私规则。
- UI 异步状态通过可独立测试的状态协调器解决，不依赖点击节流掩盖竞态。
- 每项改动遵循测试先行，先证明旧行为失败，再实现最小修复。

## 1. 地块创建原子化与标准响应

### 当前问题

`FieldService.create()` 先提交 `field.create()`，再单独执行 PostGIS `UPDATE`。第二步失败时，接口报错但地块已经存在。创建响应也不包含最终的 `lng/lat`。

### 设计

`FieldService.create()` 使用 Prisma 交互式事务：

1. 在事务中创建地块基础记录。
2. 在同一事务连接中使用参数化原生 SQL 写入 `geography(Point, 4326)`。
3. 在事务中重新读取基础字段和 `ST_X/ST_Y` 坐标。
4. 返回与列表接口一致的 `FieldView`。
5. 事务成功后再失效公开溯源租户缓存。

原生 SQL 必须继续使用参数绑定；不拼接用户输入。若坐标写入或回读失败，整个事务回滚。

### 验收

- 坐标 SQL 失败时 `field.create` 不产生持久记录。
- 返回值含真实 `lng/lat`，不需要前端以 `null` 补齐。
- 商户和系统管理员的 owner scope 行为保持不变。
- 缓存只在成功提交后失效。

## 2. 公开地块坐标隐私

### 租户策略

新增租户级公开坐标模式：

- `hidden`：默认值；公开响应的 `fieldLng/fieldLat/tiandituKey` 均为 `null`。
- `approximate`：经纬度在后端统一降精度到小数点后两位，再进入公共 DTO。
- `exact`：租户明确启用后返回精确坐标。

存量租户和新租户都采用 `hidden`，避免迁移后意外扩大公开范围。

### 配置边界

租户系统管理员可读取和更新本租户公开展示配置。平台对其他租户的管理仍遵循现有平台权限边界。公开查询接口不接受客户端传入的坐标模式。

配置包含：

- `publicCoordinateMode`
- `brandName`
- `industryName`
- `defaultCropName`
- `workbenchTitle`
- `defaultBaseLabel`

所有字段有长度限制和默认值；空字符串归一化为默认值，不允许用配置注入 HTML。

### 公共投影

`PublicTraceService` 在构造公开响应前读取租户配置，并按模式投影坐标：

- `hidden` 不必查询或返回地图密钥。
- `approximate` 只返回降精度后的坐标。
- `exact` 保留现有地图行为。

缓存键对应的响应已经包含最终隐私投影。更新租户配置后必须失效该租户全部公开溯源缓存。

### 验收

- 未配置租户的公开扫码不出现地图和坐标。
- 模糊模式不得通过其他响应字段泄露原始坐标。
- 精确模式保持现有地图展示。
- 配置更新后 30 秒缓存 TTL 内也能立即生效。

## 3. 小程序溯源请求竞态

### 当前问题

多个 `loadEvents(batchId)` 并发时，较早请求可能最后返回并覆盖当前批次的事件、错误或 loading。

### 设计

页面维护单调递增的请求序号：

1. 每次加载分配新的 request ID，并立即切换 `selectedId`。
2. 成功、失败和 finally 更新前都检查该 ID 是否仍是最新请求。
3. 旧响应被静默丢弃。
4. 页面卸载后不更新状态。

将“是否接受响应”的纯逻辑提取为小型、可单测的协调器，页面仅负责调用。

### 验收

- A 慢、B 快时最终只显示 B。
- A 的失败不能覆盖 B 的成功状态。
- A 的 finally 不能提前关闭 B 的 loading。

## 4. Web Dialog FIFO 队列

### 当前问题

全局仅保存一个 `currentDialog`。后一个对话框会覆盖前一个，导致前一个 Promise 永不结束。

### 设计

将状态改为：

- 一个当前请求。
- 一个 FIFO 等待队列。
- `confirmDialog` 和 `alertDialog` 统一入队。
- 当前请求完成后自动激活下一项。
- `DialogHost` 最后一个订阅者卸载时，当前请求按取消处理，队列中所有请求也按各自取消语义完成，禁止悬挂 Promise。

确认框取消返回 `false`；警告框取消或卸载均 resolve `void`，保持现有公开 API。

### 验收

- 连续两个确认框按顺序展示并分别 resolve。
- confirm 与 alert 混合调用保持调用顺序。
- Host 卸载后没有未完成 Promise。
- 现有单对话框交互和无原生 `alert/confirm` 约束继续通过。

## 5. 扫码计数与防伪明细一致性

### 当前问题

`scanCount` 先增加，`traceScan.create()` 失败被吞掉，导致累计次数、风控明细和公开响应永久不一致。

### 设计

当请求携带扫码元数据时，在同一个数据库事务内：

1. 创建 `TraceScan` 明细。
2. 原子增加 `TraceCode.scanCount`。
3. 返回更新后的计数。

任一步失败则事务回滚，公共接口返回服务错误，不发布虚假的累计次数。没有元数据的受控调用仍只执行原子计数更新，保持现有调用兼容性。

错误通过现有结构化日志/指标链路记录，但不把 IP、User-Agent 或数据库内部错误返回给公众。

### 验收

- 明细写入失败时扫码数不增加。
- 计数更新失败时明细不残留。
- 成功时响应计数、数据库计数和明细数量同步增加。
- 冻结码仍不增加计数、不写明细。

## 6. SaaS 品牌与行业文案配置

### 数据流

新增当前租户品牌配置读取接口，由已登录 Web 和小程序共用：

```text
Tenant settings
  -> protected backend endpoint
  -> shared runtime schema
  -> Web branding context / miniapp branding store
  -> navigation, workbench, poster and empty-state copy
```

默认值保持当前产品可识别性，但不虚构具体基地：

- `brandName`: 租户名称
- `industryName`: `农业`
- `defaultCropName`: `作物`
- `workbenchTitle`: `农业工作台`
- `defaultBaseLabel`: `当前基地`

小程序编译期 `navigationBarTitleText` 使用通用标题，登录后通过 `Taro.setNavigationBarTitle()` 应用租户工作台标题。这样不会要求每个租户单独编译小程序。

### 替换范围

只替换生产路由中的硬编码：

- 小程序工作台标题、无批次回退文案、溯源海报标题。
- Web 导航中的“我的芍药档案”。
- 商户批次管理中的搜索、按钮和表头行业文案。

示例输入 placeholder 可使用配置后的作物名。明确隔离的 `DashboardDemo`、`dashboard-demo/*` 和 `legacy/*` 不纳入替换。

### 失败行为

配置请求失败时使用通用默认值，不能阻断登录、农事记录或溯源主流程。后台保存失败必须保留表单输入并显示真实错误。

### 验收

- 非芍药租户的生产页面不再显示芍药、白芍或基地 A 区。
- 两个租户可以展示不同标题和默认作物。
- 配置失败时展示通用文案而非旧的行业硬编码。
- 演示区继续明确标注为演示，不被误认为生产数据。

## 7. 迁移与兼容性

使用 Prisma migration 增加租户配置字段或一对一租户设置表，最终实现选择以保持现有 `Tenant` 模型清晰和迁移可回滚为准。数据库默认值必须与 Shared DTO 默认值一致。

公开 DTO 保留可空 `fieldLng/fieldLat`，避免破坏现有消费者；行为变化是默认从精确值变为 `null`。字段不删除。

所有新增接口使用现有 JWT、角色和租户 scope，不创建匿名配置修改接口。

## 8. 测试与验证

每个问题独立执行 RED → GREEN → REFACTOR：

1. Backend：
   - 地块事务失败回滚与最终响应。
   - 三种坐标隐私模式与缓存失效。
   - 扫码计数/明细事务一致性。
   - 租户配置权限、校验和默认值。
2. Web：
   - Dialog 并发队列和卸载清理。
   - 品牌配置驱动导航与批次文案。
   - 公开地图仅在坐标和地图密钥都可用时展示。
3. Miniapp：
   - 快速切换批次的乱序响应。
   - 配置成功与失败回退。
   - 动态导航标题和海报标题。
4. Shared：
   - 新增配置 schema 和坐标模式 schema。
5. 完整门禁：
   - 相关包定向测试。
   - Prisma generate/migration 校验。
   - Backend、Web、Miniapp 构建。
   - `pnpm verify:production`。

若生产级 E2E 因数据库、Docker、微信开发工具或外部地图环境不可用而受阻，必须准确报告受阻范围，不以单元测试替代完整验证声明。

6. 小程序请求竞态。
7. Web/小程序 SaaS 文案接入。
